# T7 M2 — Design: pipeline attestation (signing + verifier)

> Status: **DESIGN, awaiting CEO go for M2 implementation.** CEO ruling
> 2026-09-01: M2 authorized only after the three prerequisites below are
> designed to completion. This document is that design. No code until go.
>
> M1 (D-174) is live: the broker, trailers, run-id, prompt capture. M2
> adds the signature, the trust anchor, durable evidence, and the
> verifier. It changes what a commit *proves*, not what the pipeline does.

## 0. Attestation semantics (prerequisite 3 — stated for the record)

Every M2 artifact (verifier output, docs, commit trailers) carries this
exact semantics:

> The `Swbp-*` trailers record what the **trusted pipeline recorded**:
> the model id it observed on its own call path (provider-returned when
> the server reports one, else the role's mapped model, else `unset`),
> the run, the task, the plane, and the hashes of the prompt/reply bytes
> it archived. The GPG signature attests that **the pipeline's broker
> made this commit with these trailer values**. It does **not**
> independently prove which model generated a reply; only the pipeline's
> own call path (`llm-call.sh` seat check, D-62) can make that claim.
> The provider-returned model id is the **server's own claim** about
> which model served the call, recorded by the pipeline and attested by
> the signature.

Provider-returned identifiers are preferred over environment variables
wherever available (M1 already does this for the model id via the meta
sidecar). M2 extends the same preference to the provider's call
receipt: the response envelope's `id` field (already captured in the
meta sidecar as `call_id=`) becomes trailer **`Swbp-Call-Id:`** when
present — the provider's own receipt for the call, recorded and
attested, never fabricated.

## 1. Trust anchor (prerequisite 1)

### 1.1 The key

- **Dedicated pipeline key**, generated by `swbp-provenance init`
  (new subcommand in `scripts/git-provenance.sh`):
  - algorithm: **EdDSA (Ed25519)** — small, fast, no RSA parameter risk;
  - uid: `swbp-provenance@swbp.invalid` (machine identity, RFC 6761
    reserved domain — never routable, consistent with M1 author emails);
  - **no passphrase** — the pipeline signs unattended mid-run; the
    security model is file location + permissions, not a prompt;
  - **expiry: 2 years** — forces the rotation cycle to actually happen;
  - private key: `~/.swbp/provenance/provenance-key.gpg` (0600).
    Outside the repo, outside the sandbox (the model's filesystem view
    is the project CWD — it cannot read or use the key; D-127 already
    blocks `.git` writes, this extends the same boundary to the key);
  - public key: committed to the child repo at
    `scripts/.provenance/pub.asc` (verification material — **not** the
    anchor; see 1.2).

### 1.2 The anchor: pinned fingerprints, out-of-band

A public key stored only in the repo it verifies is insufficient: a
compromised pipeline can re-pin its own key. The **anchor** is the set
of accepted key fingerprints, stored **outside the verified repo**:

- **Machine tier (authoritative for gate mode):**
  `~/.swbp/provenance/pinned-fingerprints` — one 40-hex fingerprint per
  line, with a comment header naming the key uid and the date pinned.
  The CEO (or an operator with the CEO's authorization) is the only
  writer. The verifier in gate mode requires:
  `signing key fingerprint ∈ pinned AND ∉ revoked`.
- **Public tier (portability):** the same fingerprint list is published
  in the Blueprint (`docs/PROVENANCE.md`, committed and itself visible
  in history) so a third party can check "is this the project's
  pipeline key?" The public tier is documentation; the machine tier is
  the gate. They must agree — a selftest compares them in the
  Blueprint repo.
- The in-repo `pub.asc` is convenience material for `gpg --verify`; the
  fingerprint check against the pinned list is what gate mode trusts.

### 1.3 Rotation

`swbp-provenance rotate` — designed for zero-downtime overlap:

1. Generate the new key (same uid, new fingerprint); private key to
   `~/.swbp/provenance/provenance-key.gpg` (old key preserved as
   `provenance-key-<oldfp8>.gpg`).
2. Export the new public key; the pipeline commits an updated
   `scripts/.provenance/pub.asc` (a **bundle** — both keys while
   overlapping) — signed by the OLD key (the last commit the old key
   attests).
3. The CEO adds the new fingerprint to `pinned-fingerprints` (machine
   tier) and to `docs/PROVENANCE.md` (public tier) — out-of-band of the
   pipeline.
4. The pipeline switches to the new key (the broker reads the active
   key file; `swbp-provenance active` shows which).
5. After one clean adoption cycle on the new key, the old key is
   retired: its fingerprint moves from `pinned-fingerprints` to
   `revoked-fingerprints` (retire ≠ revoke for compromise — see 1.4 —
   but an expired/retired key must stop gating new commits).

During the overlap, the verifier accepts **any** fingerprint in the
pinned list — both keys verify. The overlap window is bounded by the
rotation procedure, not by the key expiry.

### 1.4 Revocation

`swbp-provenance revoke <fingerprint>`:

- moves the fingerprint from `pinned-fingerprints` to
  `~/.swbp/provenance/revoked-fingerprints` (0600, append-only in
  practice — the file's own history is the audit trail);
- **revocation takes precedence over pinning**: a fingerprint present in
  both files is treated as revoked;
- revocation is permanent (a revoked fingerprint never returns; a new
  key is a new fingerprint);
- trigger: key compromise, or operator error (wrong key pinned).
  Retirement (end of a rotation) also lands in the revoked file, marked
  with a `# retired` comment for audit clarity.

### 1.5 What must be signed

- **Every broker commit** — all five roles, including `human`-role
  broker commits (`[template-*]`, bootstrap). The broker is the single
  commit path; the signature is the broker's fingerprint on that path.
- **Non-broker commits** (the CEO's manual commits, hand edits) are
  **out of scope** — unsigned, not failed. The verifier's scope is
  pipeline commits, identified by: a `Swbp-Role:` trailer present, OR a
  pipeline subject prefix (`[plan]`, `[task …]`, `[success]`,
  `[refreeze vN]`, `[template-*]`, bootstrap).
- **The hole the verifier must catch:** a commit with a pipeline subject
  but **no** `Swbp-Role:` trailer = a non-broker pipeline commit = the
  exact gap M1 closes. Gate mode **fails** on it (report mode warns).

## 2. Durable evidence storage (prerequisite 2)

### 2.1 The problem

M1 trailer hashes point at bytes in `.coder-archive/` / `.em-archive/`
— self-ignoring, CWD-local, wiped at success teardown. After a push or
a machine loss, `Swbp-Prompt-SHA256` is unreverifiable. A hash without
durable bytes is a label, not evidence.

### 2.2 Design: evidence committed atomically with the commit

- New path in the child repo: **`.swbp-evidence/<run-id>/<entry>/`**
  where `<entry>` is:
  - `[plan]` → `plan-<seq>/` (seq = plan attempt within the run)
  - `[task]` → `<task-id>-a<attempt>/`
  containing `prompt.txt` (exact bytes the model received),
  `reply.raw` (exact bytes the model returned), `meta.txt` (model=,
  call_id=, ts=).
- The broker commits the evidence **in the same commit** as the
  `[plan]`/`[task]` message (the trailer hashes are computed over
  exactly these bytes). Atomicity is the point: trailer and bytes live
  in the same commit object, so verification needs only the repo — no
  sidecar, no separate ref, no external store.
- **Why not a separate evidence branch or repo:** cross-ref binding
  weakens the proof (two things to fetch, two things to drift) and adds
  operational surface. The history-bloat cost is small and bounded:
  prompts/replies are KB-scale (a 20-attempt milestone ≈ 1–2 MB), and
  the evidence IS the provenance record T7 exists to create.
- **Size guard (fail-closed):** if any evidence file exceeds 5 MB, the
  broker dies without committing (never silently truncate — a truncated
  byte stream makes the hash a lie). Realistic LLM replies are <100 KB;
  the guard is a tripwire, not an expectation.
- `[success]` teardown stops wiping the CWD archives' *evidence
  relevance* — the CWD archives (`.coder-archive/` etc.) remain for
  between-run debugging and stay git-ignored; the git-committed copy
  under `.swbp-evidence/` is the durable record. `.swbp-evidence/` is
  **not** git-ignored.
- **Persistence by remote:** Vortex/Testchat push to their own remotes,
  so their evidence survives machine loss. rich-adoption (D-165: no
  remote) has local-only persistence — acceptable for an experiment;
  the mechanism is identical.

### 2.3 Binding and verification

- `Swbp-Run:` ↔ the `<run-id>` directory name (one run, one directory).
- `Swbp-Task:` + attempt ↔ the `<entry>` name for `[task]` commits.
- `Swbp-Prompt-SHA256` / `Swbp-Reply-SHA256` / `Swbp-Call-Id:` ↔
  sha256 of `prompt.txt` / `reply.raw` and the `call_id=` line of
  `meta.txt`, recomputed by the verifier from the commit tree.
- A tampered evidence byte (any later commit modifying
  `.swbp-evidence/` under an existing run-id) is detected: the verifier
  recomputes hashes for the **original** commit's tree and also checks
  that no later commit in the range modifies that run's evidence path
  (evidence is append-only per run by construction).

## 3. The verifier — `scripts/check-provenance.py`

### 3.1 Interface

```
check-provenance.py <range> [--gate] [--pinned <file>] [--revoked <file>]
                    [--report]
```

- `<range>`: any git rev range (default: `HEAD~50..HEAD` in a child;
  CI passes the push range).
- `--pinned` / `--revoked`: default to the machine-tier files under
  `~/.swbp/provenance/`.
- **Report mode (default):** a per-commit table — subject, role, model,
  run, plane, signature status (valid / invalid / missing /
  wrong-key / revoked), evidence status (matches / mismatch / absent).
  Warnings only; exit 0. This is the advisory-teeth stage (house
  pattern: advisory first, real teeth after one clean cycle).
- **Gate mode (`--gate`):** exit non-zero on any: invalid/missing
  signature on a broker commit; fingerprint not pinned or revoked;
  pipeline-subject commit without `Swbp-Role:`; malformed trailers
  (role/model/plane/run well-formedness); evidence hash mismatch or
  tampered evidence path.
- GPG verification uses `gpg --status-fd` (machine-readable) against the
  committed `pub.asc` bundle; the fingerprint is then checked against
  the pinned/revoked lists. No network, no keyserver.

### 3.2 Adoption and gate tiering (D-170 pattern)

1. **M2a lands report-only** — wired into the child CI as an advisory
   job (T2 tier, like `doc-consistency`/`manifest-drift-guard`): it
   reports, never blocks.
2. **One clean adoption cycle:** a live run on at least one child
   (Vortex or Testchat, whichever takes the next slot) produces a full
   broker trail — `[plan]`/`[task]`/`[success]` signed, evidence
   committed, verifier report clean.
3. **M2b flips the gate:** after the clean cycle, the verifier moves to
   T1 (hard) in CI and the pre-push gate. From then on, a pipeline
   commit that cannot verify is a release failure.

### 3.3 Blind selftests (authored before implementation, house style)

Against a fixture repo with a fixture keypair (generated in-test,
pinned/revoked files under tmp):

1. Broker commit (fixture key) verifies: signature valid, fingerprint
   pinned, trailers well-formed, evidence hashes match.
2. Wrong-key commit (different fixture key, not pinned) → gate fails,
   names the fingerprint.
3. Revoked fingerprint (pinned AND revoked) → gate fails, names the
   revocation.
4. Tampered evidence: a later commit modifies
   `.swbp-evidence/<run>/…/prompt.txt` → gate fails, names the path.
5. Non-broker pipeline commit: a bare `git commit` with subject
   `[task x] attempt 1` and no trailers → gate fails (the hole).
6. Rotation overlap: two pinned fingerprints, commits signed by either
   → both verify; after the first is revoked, its commits fail and the
   second's pass.
7. `Swbp-Call-Id:` present in meta → trailer present and matching;
   absent → trailer omitted (never fabricated).
8. Size guard: a planted 6 MB reply → broker refuses to commit
   (fail-closed), nothing staged.
9. Report mode on the same failures: exit 0, every failure named in the
   table.
10. Blueprint selftest: machine-tier and public-tier fingerprint lists
    agree (when both are present in the test env).

## 4. Milestone shape

- **M2a (M):** key management (`init`/`rotate`/`revoke`/`active`),
  broker `-S` signing + `Swbp-Call-Id:` + evidence commits, verifier in
  report mode, blind selftests 1–10, CI advisory wiring. No behavior
  change for existing runs beyond the new trailers/evidence.
- **M2b (S):** the clean adoption cycle (live run), then the T1 gate
  flip in CI + pre-push, plus `docs/PROVENANCE.md` (public tier: key
  uid, fingerprints, rotation/revocation procedure, attestation
  semantics).
- Adoption by children: as with M1 — their own `update-template.sh`
  pull; the first post-M2a run is the live validation.

## 5. What M2 does NOT do

- No model-side signing or git access (D-127 stands).
- No change to gate verdicts, plan validation, or what gets committed
  beyond the evidence path.
- No keyserver, no network in verification, no passphrase prompts.
- No retroactive signing of pre-M2 history (those commits are
  out-of-scope for the gate; the verifier reports them as
  `pre-m2` and skips).
- No claim that the signature proves which model generated anything —
  the attestation semantics in §0 are the ceiling, stated everywhere.
